# Design de Tabelas no PostgreSQL

## Use esta habilidade quando

- Estiver projetando um esquema (schema) especificamente para o PostgreSQL.
- Precisar selecionar tipos de dados e restrições (constraints).
- Estiver planejando índices, partições ou políticas de segurança a nível de linha (RLS).
- For revisar tabelas visando escalabilidade e facilidade de manutenção.

## Não use esta habilidade quando

- O banco de dados de destino não for o PostgreSQL.
- Você precisar apenas de tunagem de consultas (query tuning) sem alterações no esquema.
- Precisar de um guia de modelagem agnóstico (independente de banco de dados).

## Instruções

1. Capture as entidades, padrões de acesso e metas de escala (linhas, QPS, retenção).
2. Escolha tipos de dados e constraints que garantam as regras de integridade do negócio.
3. Adicione índices para os caminhos reais de consulta e valide-os usando `EXPLAIN`.
4. Planeje o particionamento ou políticas de RLS sempre que a escala ou o controle de acesso exigirem.
5. Revise o impacto da migração e aplique as alterações com segurança.

## Segurança

- Evite executar DDL destrutivo em produção sem backups e um plano de rollback claro.
- Utilize ferramentas de migração e valide as alterações em ambiente de homologação (staging) antes de aplicar em
  produção.

## Regras Centrais

- Defina uma **PRIMARY KEY** para tabelas de referência (usuários, pedidos, etc.). Nem sempre é necessária para tabelas
  de séries temporais, eventos ou logs. Quando usada, prefira `BIGINT GENERATED ALWAYS AS IDENTITY`; use `UUID` apenas
  se houver necessidade real de unicidade global ou opacidade.
- **Normalize primeiro (até a 3NF)** para eliminar a redundância de dados e anomalias de atualização; desnormalize
  **apenas** para leituras comprovadamente problemáticas onde o ganho de desempenho (ROI) compense. A desnormalização
  prematura cria um fardo de manutenção complexo.
- Adicione **NOT NULL** em todos os campos onde a regra de negócio exigir; defina valores padrão (**DEFAULT**) para
  campos comuns.
- Crie **índices para os caminhos que você realmente consulta**: chaves primárias/únicas (automáticos), **colunas de
  chave estrangeira (FK - manual!)**, filtros frequentes, ordenações e chaves de JOIN.
- Prefira **TIMESTAMPTZ** para horários de eventos; **NUMERIC** para valores monetários; **TEXT** para strings;
  **BIGINT** para números inteiros e **DOUBLE PRECISION** para números de ponto flutuante (ou `NUMERIC` para aritmética
  decimal exata).

## Pegadinhas ("Gotchas") do PostgreSQL

- **Identificadores**: Nomes não entrelaçados em aspas são convertidos automaticamente para letras minúsculas. Evite
  nomes com letras maiúsculas ou mistas. Convenção: use sempre `snake_case` para tabelas e colunas.
- **Unique + NULLs**: Uma restrição UNIQUE padrão permite múltiplos valores NULL. Use `UNIQUE (...) NULLS NOT DISTINCT`
  (a partir do PG15) se quiser restringir para apenas um NULL.
- **Índices em FK**: O PostgreSQL **não** cria índices automaticamente para colunas de chave estrangeira (FK).
  Adicione-os manualmente para acelerar JOINs e evitar travas de lock ao atualizar/deletar na tabela pai.
- **Sem coerção silenciosa**: Estouro de tamanho ou precisão resulta em erro (não há truncamento silencioso). Exemplo:
  inserir 999 em um `NUMERIC(2,0)` falhará com erro, ao contrário de outros bancos que truncam ou arredondam sem avisar.
- **Lacunas em Sequences/Identity**: Gaps em sequências de IDs são normais (não tente "corrigi-los"). Rollbacks, crashes
  e transações concorrentes criam lacunas (ex: 1, 2, 5, 6...). Esse é o comportamento esperado para garantir
  performance.
- **Armazenamento em Heap**: Não há PK clusterizada por padrão (diferente do SQL Server ou MySQL InnoDB). O comando
  `CLUSTER` faz uma reorganização pontual e única, que não é mantida em inserções subsequentes. A ordem física no disco
  segue a ordem de inserção.
- **MVCC**: Operações de UPDATE/DELETE deixam registros mortos (*dead tuples*). O processo de `VACUUM` cuida deles.
  Desenhe o esquema para evitar atualizações massivas e frequentes em linhas muito largas (*hot wide-row churn*).

## Tipos de Dados

- **IDs**: Prefira `BIGINT GENERATED ALWAYS AS IDENTITY` (`GENERATED BY DEFAULT` também é aceitável). Use `UUID` apenas
  para fusão/federação de dados, sistemas distribuídos ou quando precisar de IDs opacos. Gere com `uuidv7()` (se estiver
  no PG18+) ou `gen_random_uuid()` (em versões anteriores).
- **Inteiros**: Prefira `BIGINT`, a menos que o espaço em disco seja extremamente crítico; use `INTEGER` para intervalos
  menores e evite `SMALLINT`.
- **Decimais/Flutuantes**: Prefira `DOUBLE PRECISION` em vez de `REAL`. Use `NUMERIC` para cálculos decimais exatos.
- **Strings**: Prefira `TEXT`. Se precisar limitar o tamanho por regra de negócio, use `CHECK (LENGTH(coluna) <= n)` em
  vez de `VARCHAR(n)`. Evite `CHAR(n)`. Use `BYTEA` para dados binários. Strings ou binários grandes (>2KB) são
  armazenados automaticamente no TOAST com compressão. Estratégias do TOAST: `PLAIN` (sem TOAST), `EXTENDED` (comprime +
  fora da tabela principal), `EXTERNAL` (fora da tabela, sem compressão), `MAIN` (comprime, mantém na tabela se
  possível). O padrão `EXTENDED` costuma ser o ideal.
- **Case-Insensitive**: Para lidar com acentuação/localidade, use colações não-determinísticas; para ASCII simples,
  prefira índices baseados em expressões usando `LOWER(coluna)` ou o tipo `CITEXT`.
- **Moeda**: Use sempre `NUMERIC(p,s)` (nunca float ou o tipo nativo `money`).
- **Tempo/Data**: Use `TIMESTAMPTZ` para carimbos de data/hora; `DATE` para apenas data; `INTERVAL` para durações. Evite
  `TIMESTAMP` (sem fuso horário). Use `now()` para o início da transação e `clock_timestamp()` para o horário real do
  relógio de parede.
- **Booleanos**: Use `BOOLEAN` combinado com `NOT NULL`, a menos que precise de uma lógica de três estados (true, false,
  null).
- **Enums**: Use `CREATE TYPE ... AS ENUM` apenas para conjuntos de dados pequenos e estáticos (ex: dias da semana).
  Para status de negócio que evoluem (ex: status de pedido), prefira `TEXT` (ou `INT`) com `CHECK constraint` ou uma
  tabela de busca (lookup table).
- **Arrays**: `TEXT[]`, `INTEGER[]`, etc. Use para listas ordenadas cujos elementos internos você precisa consultar.
  Indexe com **GIN** para operadores de inclusão (`@>`, `<@`) ou sobreposição (`&&`). Evite usar arrays para modelar
  relacionamentos tradicionais; use tabelas de junção (N:M).
- **Ranges (Intervalos)**: `daterange`, `numrange`, `tstzrange`. Suportam operadores de sobreposição (`&&`) e inclusão
  (`@>`). Indexe com **GiST**. Ideal para agendamentos e vigências. Use o padrão de limites `[)` (inclusivo/exclusivo).
- **Redes (Network)**: `INET` para IPs, `CIDR` para sub-redes, `MACADDR` para endereços MAC. Suportam operadores de rede
  nativos (`<<`, `>>`, `&&`).
- **Geometria**: `POINT`, `LINE`, `POLYGON`, `CIRCLE`. Indexe com **GiST**. Considere a extensão **PostGIS** para
  necessidades geoespaciais avançadas.
- **Busca Textual (Full-Text Search)**: `TSVECTOR` para documentos e `TSQUERY` para as buscas. Indexe o `tsvector` com
  **GIN**. Sempre especifique explicitamente o idioma nas funções (ex: `to_tsvector('english', coluna)`).
- **Domains**: `CREATE DOMAIN email AS TEXT CHECK (VALUE ~ '^[^@]+@[^@]+$')` para criar tipos customizados e
  reutilizáveis com validação integrada nativa.
- **Tipos Compostos**: `CREATE TYPE endereco AS (rua TEXT, cidade TEXT, cep TEXT)`. Acessível via sintaxe
  `(coluna).campo`.
- **JSONB**: Sempre prefira `JSONB` sobre `JSON`; indexe com **GIN**. Use apenas para atributos opcionais ou
  semiestruturados. Use `JSON` puro apenas se a ordem exata das chaves originais precisar ser preservada.
- **Vetores**: Tipo `vector` fornecido pela extensão `pgvector`, usado para busca de similaridade de embeddings de IA.

### NÃO use os seguintes tipos de dados

- NÃO use `timestamp` (sem fuso horário); use `timestamptz`.
- NÃO use `char(n)` ou `varchar(n)`; use `text`.
- NÃO use o tipo `money`; use `numeric`.
- NÃO use `timetz`; use `timestamptz`.
- NÃO use precisão explícita como `timestamptz(0)`; use apenas `timestamptz`.
- NÃO use o tipo `serial`; use `generated always as identity`.

## Tipos de Tabelas

- **Regular**: O padrão do banco; totalmente durável e registrada no WAL (Write-Ahead Logging).
- **TEMPORARY**: Escopo limitado à sessão do usuário, removida automaticamente e sem log de WAL (ótima para
  processamentos temporários).
- **UNLOGGED**: Persistente, mas não resiste a quedas do servidor (crash). Escritas muito mais rápidas; ideal para
  caches ou tabelas de staging de dados.

## Segurança a Nível de Linha (Row-Level Security)

Habilite com `ALTER TABLE tabela ENABLE ROW LEVEL SECURITY`. Crie políticas de acesso baseadas no contexto do usuário
corrente, como por exemplo:
`CREATE POLICY acesso_usuario ON orders FOR SELECT TO usuarios_app USING (user_id = id_usuario_atual())`.

## Restrições (Constraints)

- **PK**: Aplica implicitamente UNIQUE + NOT NULL e cria um índice B-tree.
- **FK**: Sempre especifique as ações de remoção/atualização (`ON DELETE/UPDATE CASCADE`, `RESTRICT`, `SET NULL`).
  Lembre-se de indexar a coluna manualmente. Use `DEFERRABLE INITIALLY DEFERRED` se houver dependências circulares que
  precisem ser validadas apenas no final da transação.
- **UNIQUE**: Cria um índice B-tree. Permite múltiplos valores NULL por padrão, exceto se configurado com
  `NULLS NOT DISTINCT` (PG15+).
- **CHECK**: Validações locais à linha. Valores NULL passam automaticamente na validação (lógica tri-valorada). Combine
  com `NOT NULL` quando quiser garantir valores preenchidos e válidos: `preco NUMERIC NOT NULL CHECK (preco > 0)`.
- **EXCLUDE**: Evita a inserção de linhas que se sobreponham usando operadores específicos.
  `EXCLUDE USING gist (room_id WITH =, booking_period WITH &&)` impede reservas duplicadas para a mesma sala no mesmo
  horário. Requer índice GiST.

## Indexação

- **B-tree**: O padrão para consultas de igualdade e intervalos (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`).
- **Composto**: A ordem das colunas importa. O índice só será usado se a coluna mais à esquerda fizer parte do filtro.
  Coloque as colunas mais seletivas ou filtradas com maior frequência primeiro.
- **Cobertura (Covering Index)**: `CREATE INDEX ON tabela (id) INCLUDE (nome, email)` - Permite varreduras apenas no
  índice (*index-only scans*) retornando dados adicionais sem precisar acessar a tabela física (heap).
- **Parcial**: Para subconjuntos de dados muito acessados (ex: apenas registros ativos ->
  `CREATE INDEX ON tabela (user_id) WHERE status = 'active'`).
- **Expressão**: Para chaves calculadas dinamicamente (ex: `CREATE INDEX ON tabela (LOWER(email))`). O filtro na
  cláusula WHERE deve ser idêntico à expressão do índice.
- **GIN**: Ideal para busca em JSONB, arrays e busca textual.
- **GiST**: Ideal para dados geométricos, tipos de intervalo (ranges) e restrições de exclusão.
- **BRIN**: Para tabelas gigantescas cujos dados são ordenados naturalmente (ex: séries temporais por data de inserção).
  Ocupa um espaço ridiculamente pequeno.

## Particionamento

- Indicado para tabelas muito grandes (>100 milhões de linhas) onde as consultas filtram frequentemente pela chave de
  partição (geralmente datas).
- Também auxilia em manutenções rotineiras, como exclusão de dados antigos através do descarte de uma partição inteira
  (`DROP PARTITION`).
- **RANGE**: Comum para séries temporais (`PARTITION BY RANGE (created_at)`).
- **LIST**: Para valores discretos (ex: `PARTITION BY LIST (regiao)`).
- **HASH**: Para distribuir os dados uniformemente quando não há uma chave natural clara
  (`PARTITION BY HASH (user_id)`).
- Não utilize herança de tabelas legada. Use sempre o particionamento declarativo nativo ou extensões como o
  **TimescaleDB** (que automatiza a criação de partições e compressão).
- **Limitações**: Não existem índices UNIQUE globais; a chave de partição obrigatoriamente deve fazer parte de qualquer
  restrição UNIQUE ou PK da tabela.

## Considerações Especiais

### Tabelas com Muitas Atualizações (Update-Heavy)

- **Separe colunas quentes e frias**: Mova colunas atualizadas freneticamente para uma tabela separada para evitar o
  inchaço (*bloat*) de dados estáveis.
- **Ajuste o `fillfactor=90`** (ou menor) nas tabelas para deixar espaço livre nas páginas de disco, permitindo
  atualizações do tipo HOT (*Heap-Only Tuples*), que evitam a necessidade de atualizar os índices da tabela.
- Evite atualizar colunas que possuam índices criados sobre elas.

### Tabelas com Muitas Inserções (Insert-Heavy)

- **Minimize os índices**: Crie apenas os estritamente necessários; cada índice adicionado penaliza a velocidade de
  inserção.
- **Use comandos em lote**: Prefira o comando `COPY` ou inserções multi-linhas em vez de múltiplos `INSERT INTO`
  unitários.
- Considere o uso de chaves naturais compostas (ex: `timestamp, device_id`) se o fluxo for de séries temporais. Se
  precisar de uma chave sequencial artificial, prefira sempre `BIGINT GENERATED ALWAYS AS IDENTITY` sobre `UUID`.

### Design para Upserts (ON CONFLICT)

- Requer obrigatoriamente um índice `UNIQUE` idêntico às colunas mapeadas no alvo do conflito
  (`ON CONFLICT (coluna1, coluna2)`). Índices parciais não funcionam como alvo de upsert.
- Use a palavra-chave `EXCLUDED.coluna` para fazer referência ao valor que tentou ser inserido originalmente.

### Evolução de Esquema Segura (Safe Migrations)

- **DDL Transacional**: Quase todas as operações de alteração de estrutura (DDL) rodam dentro de transações no
  PostgreSQL e podem sofrer `ROLLBACK` em caso de erro.
- **Criação de índices concorrentes**: Use `CREATE INDEX CONCURRENTLY` em produção para evitar travar as operações de
  escrita na tabela. Atenção: este comando não pode rodar dentro de blocos de transação explícitos (`BEGIN/COMMIT`).
- Valores padrão voláteis (como `now()` ou `gen_random_uuid()`) adicionados em conjunto com restrições `NOT NULL` podem
  forçar a reescrita completa da tabela física em versões mais antigas do banco.

## Diretrizes para JSONB

- O padrão de índice GIN (`CREATE INDEX ON tabela USING GIN (jsonb_coluna);`) acelera operadores de **Inclusão** (`@>`),
  **Existência de chave** (`?`), bem como consultas em caminhos aninhados.
- Se o seu foco exclusivo for o operador de inclusão (`@>`), utilize a classe de operadores `jsonb_path_ops`
  (`CREATE INDEX ON tabela USING GIN (jsonb_coluna jsonb_path_ops);`). Ela gera índices consideravelmente menores e mais
  rápidos, embora remova o suporte ao operador de existência (`?`).
- Se precisar filtrar ou ordenar frequentemente por um campo escalar específico de dentro do JSON, extraia-o para uma
  coluna gerada armazenada e crie um índice B-tree tradicional sobre ela.
- Use constraints para validar o tipo de dado aceito na coluna JSONB se necessário, por exemplo:
  `CHECK(jsonb_typeof(config) = 'object')`.

## Exemplos Práticos

### Usuários

```sql
CREATE TABLE users
(
    user_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      TEXT        NOT NULL UNIQUE,
    name       TEXT        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX ON users (LOWER (email));
CREATE INDEX ON users (created_at);
```

### Pedidos

```sql
CREATE TABLE orders
(
    order_id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    BIGINT         NOT NULL REFERENCES users (user_id),
    status     TEXT           NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'PAID', 'CANCELED')),
    total      NUMERIC(10, 2) NOT NULL CHECK (total > 0),
    created_at TIMESTAMPTZ    NOT NULL DEFAULT now()
);

CREATE INDEX ON orders (user_id);
CREATE INDEX ON orders (created_at);
```

### JSONB e Perfis

```sql
CREATE TABLE profiles
(
    user_id BIGINT PRIMARY KEY REFERENCES users (user_id),
    attrs   JSONB NOT NULL DEFAULT '{}',
    theme   TEXT GENERATED ALWAYS AS (attrs->>'theme'
) STORED
);

CREATE INDEX profiles_attrs_gin ON profiles USING GIN (attrs);
```
